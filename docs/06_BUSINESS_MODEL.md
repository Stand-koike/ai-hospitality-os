## 2. Business Model Overview

藍 ai の事業は、**Hospitality OS** として、ソフトウェアと現場の変化をつなぐ価値連鎖を中心に置く（[02](./02_PRODUCT_DEFINITION.md)、[01](./01_BRAND_BOOK.md)）。

```text
Software
   ↓
現場で使われる
   ↓
行動が変わる
   ↓
情報が残る・共有される
   ↓
お客様への理解が深まる
   ↓
接客・関係性が変わる
```

これはプロダクトの因果モデル（行動変容 → 情報 → 共有 → 理解 → 接客 → 再訪・関係性）の **事業側の読み方**である。  
「機能を売る」だけでなく、**使われて行動が変わること**が価値の前提になる。

---

## 3. Two-Layer Model

藍 ai は **Software + Hospitality Success** の二層構造（[02 §10](./02_PRODUCT_DEFINITION.md)、[01 §6](./01_BRAND_BOOK.md)）。

### 3.1 Software

**藍 ai 本体**（再現可能なプロダクトが中心）。

Guest-centered な情報の理解・共有を支える MVP 範囲（[03](./03_MVP_SPEC.md)、[04](./04_DOMAIN_MODEL.md)、[05](./05_UI_UX.md) と整合）：

| 領域 | 内容 |
|------|------|
| プラットフォーム思想 | Guest-centered domain model（Reservation / Stay / Timeline Entry） |
| 体験 | Today's Brief（ホーム）、Guest Resolution、Guest Summary、Timeline |
| 出力 | Paper Output（Brief の安全な紙共有） |
| AI | Guest に紐づく過去情報の **要約・整理**（判断主体の AI は含めない） |

予約データの取り込み **経路**は未決定。メール解析は MVP 外（decision-log）。

### 3.2 Hospitality Success

**伴走支援** — 導入・定着・現場での活用と **行動変容**を支える。

| 方向（仮説） | 例 |
|--------------|-----|
| 初期導入 | オンボーディング、データの最初の流れ |
| 定着 | Today's Brief の使い方、Guest Resolution の運用 |
| 文化 | 気づきを Timeline に **短く残す**習慣、申し送り・朝礼との接続 |
| 確認 | 利用状況の見える化（**具体手法未決定**） |
| 学習 | 現場フィードバックの収集とプロダクト改善への反映 |

**明記する方向性**

- **コンサルティング**ではなく **伴走支援**（無制限カスタマイズの個別コンサルモデルにはしない）。
- 創業者の経験は **プロダクト・運用手順に落とし込み**、長期的に **創業者個人に依存し続けるモデル**を前提にしない（[02](./02_PRODUCT_DEFINITION.md)）。
- 具体的な **サービスメニュー・提供時間・契約形態**は **未決定**。

## 4. Customer / User

| 区分 | 現時点の想定 | 確度 |
|------|--------------|------|
| **Customer** | 宿泊施設の **経営者・運営責任者**（契約・継続の意思決定） | 仮説 |
| **User** | **現場スタッフ**、接客担当、経営者兼スタッフ | 仮説 |

7 室・個人経営パイロットでは Customer と User が **同一または重複**しうる（**要検証**）。

**購買決定者と日常利用者の関係**はパイロットで検証する（未決定）。

## 5. Initial Customer Hypothesis

[02 §3](./02_PRODUCT_DEFINITION.md)、パイロット ADR と整合する **初期ターゲット仮説**（市場規模・数値は書かない）。

- **小規模宿泊施設**（モデル：**個人経営・約 7 室・1 施設**）
- **個人経営・家族経営**が多い
- **地域性・接客・リピーターとの関係性**が強い
- スタッフが少なく、**情報共有が属人化**しやすい
- 本来のおもてなしの価値はあるが、仕組み・人手で十分に発揮できていない（B〜C クラス感は [02](./02_PRODUCT_DEFINITION.md) — 境界は未決定）

高級旅館のみ・大規模チェーンのみを想定しない。

## 7. Scalability

**目指す方向**（確定思想ではなく、検証を伴う方針）。

| 方針 | 内容 |
|------|------|
| Software | 可能な限り **再現可能**に。7 室パイロットで得た学習を仕様・プロダクトに反映 |
| Hospitality Success | 伴走内容も **段階的に標準化**（プレイブック化 **仮説**） |
| ナレッジ | 創業者・現場の知見を **プロダクトと運用手順**へ移す |
| 依存 | 「創業者が直接説明しないと価値が出ない」状態を **長期的な前提にしない** |

大規模向けの組織・権限・多拠点は MVP / 初期事業モデルの **先取り対象にしない**（[03](./03_MVP_SPEC.md)、[05](./05_UI_UX.md)）。

## 8. Pilot → Product Transition

**個人経営・7 室程度のモデル施設**（1 施設 — 名称・地域 **未決定**）での想定フロー。

```text
1. 実際に使う（Software + 必要な伴走）
2. 行動が変わるか観察する（Brief / Resolution / Summary / Timeline / 記録）
3. 何が定着を妨げるか確認する（入力負担・習慣・紙・権限等）
4. Software と Hospitality Success の役割を整理する
5. 再現可能な形へ修正する（仕様・伴走メニュー・07 価格仮説）
```

成功の **第一評価**は売上ではなく、[03 §10](./03_MVP_SPEC.md) の **行動変容・関係性**（測定方法は未決定）。

## 9. Business Model Risks / Hypotheses

**検証事項**（結論は出さない）。

| # | 検証事項 |
|---|----------|
| 1 | 宿泊施設が **どの程度の料金**なら継続利用するか（→ 07） |
| 2 | Software と伴走支援の **適切な比率・バンドル** |
| 3 | 導入時に **どの程度の伴走**が必要か |
| 4 | 伴走を **どこまで標準化**できるか |
| 5 | 現場スタッフが **継続的に使う**条件（特に Timeline への短い記録） |
| 6 | Guest-centered な価値を **経営者がどう評価**するか（定性・定量とも未決定） |
| 7 | 予約取り込み経路が未決定のまま、体験 C を **運用で回せるか** |
| 8 | Paper Output・朝礼文化との **相性**（[05](./05_UI_UX.md) Open Questions） |
| 9 | ソフト単体で価値が伝わるか、伴走なしでは **定着しないか** |
| 10 | Hospitality Success を「コンサル」化せず **スケール**できるか |
