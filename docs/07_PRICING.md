# 07 — 価格設計（藍 ai）

**バージョン**：v0.1  
**ステータス**：仮説・論点整理（MVP・パイロット前）  
**前提**：[README.md](../README.md) · [01](./01_BRAND_BOOK.md)〜[06_BUSINESS_MODEL.md](./06_BUSINESS_MODEL.md)

本書は **価格を確定する文書ではない**。**価格設計の仮説と検証事項**を整理する。

「いくらで売るか」より先に、**何に対して料金をもらうか**・**Software と Hospitality Success をどう分けるか**・**どの課金単位が自然か**・**パイロットで何を検証するか**を明確にする。

具体的な金額・市場価格・競合価格・ARR/LTV/CAC は **本書に含めない**。

## 1. Purpose

| 項目 | 内容 |

| 目的 | 現時点で考えるべき **価格設計の論点**を、既存思想と整合させて短くまとめる |
| 非目的 | 最終価格の決定、収益予測、競合ベンチマーク |

事業の価値前提（変更しない）：**現場の行動変容**が最初の価値。Software は再現可能なプロダクトの中心。Hospitality Success は **伴走支援**（コンサルティングではない）。

## 2. Pricing Principles

[06 §2–3](./06_BUSINESS_MODEL.md)、[02](./02_PRODUCT_DEFINITION.md)、[03](./03_MVP_SPEC.md) から読み取れる **価格設計の原則**（確定思想ではなく、現段階の指針）。

| # | 原則 |
|---|------|
| 1 | **機能数**ではなく、**継続的な利用価値**（現場で使われ、行動が変わること）に対して料金を考える |
| 2 | **Software** と **Hospitality Success** の価値を **混同しない**（課金の論点も分けて検討） |
| 3 | **小規模宿泊施設**（パイロット：個人経営・約 7 室）でも導入可能性を検討する |
| 4 | **現場で実際に使われる**こと（Today's Brief、Resolution、Timeline への記録等）を前提にする |
| 5 | 料金体系を **複雑にしすぎない**（MVP 段階の思想と一致） |
| 6 | 初期段階では **価格より価値検証を優先**する（パイロット） |
| 7 | 「AI 機能そのもの」「データ保存」だけを **価格の中心**にしない（§4） |

## 3. Pricing Structure Hypothesis

[06 §6](./06_BUSINESS_MODEL.md) の収益仮説を、**価格の「形」**の検討対象として展開する。**採用は未決定**。

### 3.1 Software

**継続利用**に対する料金が基本候補。

| 検討対象 | 備考 |
|----------|------|
| 月額 / 年額 | どちらを主軸にするか **未決定** |
| 施設単位 | 1 施設あたり |
| 室数ベース | 7 室パイロットとの相性を **検証** |
| ユーザー数ベース | 少数スタッフ前提 |

### 3.2 Hospitality Success

**導入・定着・活用**を支える伴走支援の料金（Software とは別価値）。

| 検討対象 | 備考 |
|----------|------|
| 初期導入費 | オンボーディング・最初のデータの流れ |
| 導入期間の伴走費 | 期間限定 **仮説** |
| 継続的な伴走費 | 定着フェーズ（必要性 **要検証**） |
| Software とのバンドル | 分離 vs 一体 **未決定** |

無制限カスタマイズの **個別コンサル型**にはしない（[06 §3.2](./06_BUSINESS_MODEL.md)）。

## 4. What Customers Are Paying For

### 4.1 Software（価値の中心）

お客様（宿）が **Software に対して支払う論点**となる価値（[03](./03_MVP_SPEC.md)、[05](./05_UI_UX.md) と整合）。

| 価値 | 内容 |
|------|------|
| 理解 | Guest 情報を **理解しやすく**する（Guest Summary、Today's Brief） |
| つながり | 予約と過去 Guest の **紐付け**（Guest Resolution） |
| 残す・共有 | 気づきを **Timeline** に残し、次のスタッフが見られる |
| 行動 | 現場の **行動変容**（Brief を見る、接客前に理解、記録する）を支える |
| AI | Guest 履歴の **要約・整理**（判断・接客指示ではない） |

**価格の中心にしない**：単なるデータ保存、AI 機能の有無だけ、経営ダッシュボード・KPI。

### 4.2 Hospitality Success（価値の中心）

| 価値 | 内容 |
|------|------|
| 導入 | 最初に **使い始められる**状態 |
| 定着 | Brief・Resolution・記録の **習慣** |
| 運用設計 | 現場フローとプロダクトの **接続**（具体メニュー **未決定**） |
| 活用支援 | フィードバック収集と改善（伴走の範囲 **未決定**） |

## 5. Pricing Unit Hypotheses

| 候補 | 検討ポイント |
|------|----------------|
| **施設単位** | 小規模宿との相性、説明の分かりやすさ |
| **室数** | 宿泊規模との連動（7 室モデルの検証） |
| **ユーザー数** | スタッフ数・兼務（個人経営では少人数） |
| **利用量** | 予約数・Guest 数等（運用コストとの関係 **未検証**） |
| **Software + 伴走** | 導入初期のパッケージとしての相性 |

**優劣は決定しない**。パイロットで「自然さ」を観察する（§7）。

## 6. Pilot Pricing

**個人経営・7 室・1 施設**（[decision-log](../decision-log/)、[06 §8](./06_BUSINESS_MODEL.md)）では、通常販売価格の確定より次を優先する。

| 優先 | 内容 |
|------|------|
| 1 | 実際に **使う** |
| 2 | **価値を感じる**（行動変容・関係性の手触り） |
| 3 | **継続利用**するか |
| 4 | **どの程度の伴走**が必要か |

**未決定**：パイロット価格、無料/有料、期間、契約条件、フィードバック提供の見返り。

---

## 7. Pricing Validation

パイロット（および初期顧客）で **価格設計に効く**確認事項。

1. 宿泊施設が **どの程度の価値**を感じるか（定性中心。**金額の妥当性は後段**）
2. **Software 単体**でも継続利用できるか、伴走が必須か
3. **伴走支援**がどの程度・どの期間必要か
4. Software と伴走を **分けて契約・説明**する必要があるか
5. **施設単位・室数・ユーザー数**など、どの課金単位が現場・経営者に自然か
6. 継続の判断材料は何か（Brief の習慣、記録の定着、リピーター接客の変化等 — 指標 **未決定**）

## 8. Current Hypothesis

現時点で言える **仮説のみ**（[06 §6](./06_BUSINESS_MODEL.md) と一致。重複を最小化）。

| # | 仮説 |
|---|------|
| 1 | Software は **継続課金**を基本候補とする |
| 2 | Hospitality Success は Software と **別の価値**として扱う |
| 3 | 初期導入には **伴走支援が必要になる可能性**がある |
| 4 | **最終的な料金体系はパイロット後**に再検討する |

具体的な金額は **書かない**。
