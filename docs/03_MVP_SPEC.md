# 藍 ai — MVP Specification
**バージョン**：v0.2  
**ステータス**：MVP 仕様（実装前）  
**前提ドキュメント**：[README.md](../README.md) · [01_BRAND_BOOK.md](./01_BRAND_BOOK.md) · [02_PRODUCT_DEFINITION.md](./02_PRODUCT_DEFINITION.md) · [decision-log/](../decision-log/)
## 1. MVP Definition
藍 ai の MVP は、**Hospitality OS** として、宿泊施設の現場における **行動変容** を起こすための最小プロダクトセットである。
- **Reservation（予約）** は一時的なイベント。
- **Guest（お客様）** は継続する存在。情報は Guest ID に集約する。
- **ホーム画面** は **Today's Brief**。経営ダッシュボードではない。
MVP が直接狙う成果指標は、売上・評価・再訪率ではない。まず **宿泊施設で働く人の行動** が変わるかを見る。

**因果モデル（確定）**

```
行動が変わる → 情報が残る → 情報が共有される → お客様への理解が深まる
→ 接客が変わる → 再訪・関係性につながる → 結果として宿の価値が高まる
```

**仕様の評価基準**

> この機能によって、現場の行動が本当に変わるか。

機能の数・画面の多さは評価に使わない。

**ADR との整合**

- 予約メール解析は MVP に含めない：[20260918-no-reservation-email-parsing.md](../decision-log/20260918-no-reservation-email-parsing.md)
- パイロット施設：[20260918-model-property-pilot.md](../decision-log/20260918-model-property-pilot.md)

## 2. MVP Goals
| 目標 | 内容 |
|------|------|
| 主目標 | 現場スタッフの **行動** を、設計したフローに沿って変える |
| 体験 A | 今日来るお客様を **短時間で理解** できる |
| 体験 C | 予約が入った瞬間、**過去のお客様とのつながり** が見える |
| 非目標 | 売上最大化、レビュー改善、再訪率の直接改善、経営分析の提供 |
## 3. Core User Experiences
### A. Today's Guest Understanding（体験 A）
**確定**：今日来るお客様を短時間で理解できる。
スタッフがチェックインや当日対応の前に、Today's Brief → Guest Summary（必要なら Timeline）を辿り、**その人に合った接客の準備**ができる状態を指す。
### C. Guest Resolution（体験 C）
**確定**：予約が入った瞬間、過去のお客様とのつながりが見える。
新規予約が藍 ai に入ったとき、**既存 Guest との関係**（候補・過去滞在・文脈）がすぐに確認でき、Reservation が Guest に紐付くことで体験が完結する。
**重要なプロダクト仮説（要検証）**
Guest Resolution が、リピーター比率の高い小規模宿において、関係性の継続に効く可能性がある。現時点で「技術的な最大の強み」などと断定しない。

## 5. MVP User Flow
### 5.1 一日の基本フロー（到着中心）
```
Today's Brief（ホーム）
  ↓ 本日の到着 / 出発を確認
  ↓ 到着 Guest を選択
Guest Summary
  ↓ 必要に応じて
Timeline
```

### 5.2 予約が入ったとき（体験 C）

```
予約データが藍 ai に入る（取り込み経路：未決定）
  ↓
Guest Resolution（候補提示）
  ↓ 一致情報の確認
  ↓ スタッフが判断
Reservation → Guest ID に紐付け
  ↓
Guest Summary / Timeline で文脈を確認可能
```

### 5.3 朝礼・申し送り（Paper Output）

```
Today's Brief
  ↓ 印刷（内容・レイアウト：未決定）
紙でチーム共有（朝礼・フロント周辺・厨房等：施設による）
```

## 6. Feature Specifications
以下、各機能を同一フォーマットで定義する。
---
### 6.1 OTA Reservation Ingestion
（名称は「OTA 予約の取り込み」。**OTA メール解析ではない**。）
#### Purpose
予約データが **藍 ai 上に存在**し、Guest Resolution・Today's Brief の入力になる状態を作る。
#### Current Problem
予約は OTA・電話・直接予約など複数経路に散らばり、**「今日誰が来るか」「この予約は以前のお客様か」** がシステムを横断して見えない。紙・頭・個人のメモに依存し、引き継ぎで文脈が消える。
#### Behavior Change
- 予約が発生したら、スタッフが **藍 ai を開いて予約を確認する**（取り込み操作は経路に依存するが、確認の習慣は共通）。
- 予約を見たスタッフが **「このお客様は以前にも来ているかもしれない」** と気付き、Guest Resolution に進む行動が生まれる（体験 C の入口）。

#### User Flow

```
（未決定：手動登録 / ファイル取込 / API 等）
  ↓
予約がシステム上に 1 件として存在
  ↓
Guest Resolution フローへ（6.2）
  ↓
Today's Brief に本日到着として反映
```

#### Information Displayed

MVP で予約レコードに持たせる情報（**各項目の必須/任意は未決定**）：

- 宿泊者名（または代表者名）
- チェックイン日・チェックアウト日
- 連絡先（電話・メール等）
- 予約の取り込み元・登録日時（監査用の最小メタデータ：**要検証**）
- Guest 紐付け状態（未解決 / 紐付け済）

#### Input

- **取り込み経路：未決定**（手動、CSV、OTA API、エクスポート等は **仮説・将来検討** のみ。いずれも採用を確定しない）
- 経路が決まるまで、仕様上は「予約データを藍 ai に登録できること」だけを要求する
- 新規入力項目を増やす場合は、行動変容とセットで再評価する（原則 4）

#### AI Usage

MVP では **予約取り込みそのものに AI は必須としない**（未決定：将来の抽出支援は Phase 2 以降）。

#### Acceptance Criteria

- パイロット施設（7 室）で、**当日および将来の到着予約**が藍 ai 上で一覧できる。
- 予約作成後、**未紐付けの予約**が識別でき、Guest Resolution に遷移できる。
- **予約メール解析に依存しない**（ADR 準拠）。

#### Open Questions

- 具体的な取り込み経路（**未決定**）
- 部屋番号・部屋タイプ・人数・料金を MVP で持つか（**未決定**）
- 複数 OTA チャネルの識別方法（**未決定**）

### 6.2 Guest Identity / Guest Resolution
#### Purpose
予約が入ったとき **「この予約はどの Guest か」** を、人の確認を前提に解決し、**Reservation → Guest** を確立する。
#### Current Problem
同じお客様が別名・別メールで予約すると **別人として扱われ**、過去の配慮や関係性が接客に活かされない。逆に、勘違いで同一視すると失礼になる。属人化した記憶頼みになり、共有されない。
#### Behavior Change
- 予約を確認したスタッフが、**候補 Guest を見て過去の滞在・文脈を確認する**行動が生まれる。
- **「新規 Guest として登録」「既存 Guest に紐付け」「別人として扱う」** を、システム上で明示的に選ぶ行動が生まれる（完全自動に任せない）。
- 紐付け後、**次のスタッフも同じ Guest ID から** Summary / Timeline を開ける。
#### User Flow
```
予約情報が存在
  ↓
候補 Guest のリスト（照合キーに基づく：詳細は未決定）
  ↓
一致理由の表示（例：同一メール・類似氏名等：表示項目は未決定）
  ↓
スタッフが確認・選択
  ↓
Guest ID に紐付け完了
  ↓
Guest Summary / Timeline が利用可能
```

#### Information Displayed

- 予約側：氏名、連絡先、日程（6.1 と整合）
- 候補 Guest ごと：表示名、過去滞在回数、直近滞在日、照合に使った一致項目（**未決定**：何を見せるか）
- 紐付け状態：未解決 / 解決済

#### Input

- スタッフの **判断操作**（紐付け・新規作成・保留：**保留を MVP に含めるかは未決定**）
- 照合に使う属性の必須セット：**未決定**（氏名・電話・メール・過去予約等は検討候補）

#### AI Usage

- MVP では **自動同一判定のみで完結しない**（原則 7）。
- **仮説**：将来、候補の並び替えや説明文案の整理に AI を使う余地はあるが、MVP 必須ではない（**未決定**）。

#### Acceptance Criteria

- 未紐付け予約に対し、**少なくとも 0 件以上の候補**を提示できる（0 件のときは新規 Guest 作成フロー）。
- スタッフが **意図的に** 既存 Guest を選び、紐付け後に Guest Summary で過去文脈が見える。
- 誤紐付けの防止のため、**確認ステップを挟める**（UI 詳細は未決定）。
- 自動マージのみで Guest が結合されない。

#### Open Questions

- 照合アルゴリズム・スコアリング（**未決定**）
- 表記ゆれ（旧姓・ローマ字等）の扱い（**要検証**）
- 「同一人物」の最終責任者（常にスタッフか：**確定思想**、例外フローは未決定）

### 6.3 Today's Brief
#### Purpose
**今日の現場が、お客様を理解して仕事を始めるための入口**（ホーム画面）。
#### Current Problem
朝、何から手を付けるか曖昧で、**到着客の文脈確認が後回し**になる。売上や稼働だけ見ても、接客の準備には直結しない。申し送りが口頭のみで、抜けが出る。
#### Behavior Change

- スタッフが **業務開始前（または当日最初のルーティン）に Today's Brief を開く**行動が生まれる。
- **本日到着・本日出発**を一覧し、**Guest Resolution 未完了**を見逃さず対応する行動が生まれる。
- 到着 Guest をタップし、**Guest Summary へ進んで理解を深める**行動が生まれる。

#### User Flow

```
Today's Brief（ホーム）
  ↓
本日の到着 / 出発
  ↓
（未解決予約があれば）Guest Resolution へ
  ↓
Guest 選択
  ↓
Guest Summary
  ↓
（必要なら）Timeline
```

#### Information Displayed

MVP で検討する表示（**過不足はパイロットで要検証**）：

- 本日到着 Guest 一覧（名前・到着/滞在日程の最小表示）
- 本日出発 Guest 一覧（同様の最小表示）
- Guest Resolution **未完了**の件数またはバッジ
- リピーターかどうかの **一目で分かる最小指標**（例：過去滞在回数 1 以上：**表示形式は未決定**）
- Guest Summary への導線

**入れないもの（確定）**：売上、稼働率、KPI ランキング、経営分析グラフ。

#### Input

- 基本的に **閲覧のみ**。メモ入力は Guest Summary / Timeline 側（6.4 / 6.5）
- Paper Output 起動（6.6）

#### AI Usage

- **仮説**：当日の到着順の並び替えや「要確認」ハイライトに AI を使う余地はあるが、MVP 必須ではない（**未決定**）。

#### Acceptance Criteria

- 7 室規模で、**スクロール中心で当日の全体像**が把握できる。
- 未紐付け予約が **Today's Brief 上で識別**できる。
- Guest Summary に **3 タップ以内**（目安）で到達できる。速度を優先し、3 タップは絶対条件ではない（02 準拠）。

#### Open Questions

- 出発 Guest の情報量（最小でどこまでか：**未決定**）
- メニュー項目の最終構成（**未決定**）

---

### 6.4 Guest Summary

#### Purpose

選択した Guest について、**今回の予約と過去の関係性**を短時間で把握する（体験 A の主画面）。

#### Current Problem

情報が Timeline・紙・個人メモに分散し、**チェックイン直前に全体像を把握する時間**がない。履歴が長いと読む気が失せ、関係性を活かした接客ができない。

#### Behavior Change

- チェックイン前に、スタッフが **Guest Summary を開いて要点を把握してから接客に入る**行動が生まれる。
- 長い履歴を **AI 要約で先に読み**、必要なときだけ Timeline で深掘りする行動が生まれる（認知負荷の削減）。
- 業務上必要な注意事項（アレルギー等）を **見落とさず確認する**行動が生まれる（項目は最小限）。

#### User Flow

```
Today's Brief または予約一覧
  ↓
Guest Summary
  ↓
（必要なら）Timeline
  ↓
（接客後）Timeline に短いメモ追記
```

#### Information Displayed

MVP で表示する情報（**増やしすぎない**）：

| 区分 | 内容 |
| 今回 | 紐付いた予約（日程・状態） |
| 関係 | 過去滞在回数、直近滞在の概要 |
| 業務 | アレルギー・食事等の **既にシステムにある** 最小項目（入力経路は未決定） |
| 関係性 | Relationship / Memory の **最小表示**（長文一覧は Timeline へ） |
| AI | Phase 1 **要約**（下記 AI Scope） |
#### Input
- **原則**：新規入力は Timeline への短いメモに集約（負担分散）
- Summary 上での編集は **未決定**（MVP では閲覧中心を推奨：**仮説**）
#### AI Usage

- **入力**：Guest に紐づく Timeline エントリ、既存の短いメモ・滞在メタデータ（範囲 **未決定**）
- **処理**：要約・情報整理（Phase 1）
- **出力**：読みやすい短文要約。**お客様の評価・ランク・断定的な接客指示は出さない**

#### Acceptance Criteria

- 紐付け済み Guest で、**今回予約＋過去回数＋要約**が 1 画面（スクロール可）で把握できる。
- 要約は **参考情報**であり、スタッフが Timeline で根拠を追える導線がある（根拠の見せ方は **未決定**）。
- 「画面が表示される」だけでなく、**チェックイン前に Summary を見た**という運用がパイロットで説明可能。

#### Open Questions

- 要約の更新タイミング（リアルタイム / 日次：**未決定**）
- 業務情報の MVP 最小フィールドセット（**未決定**）

### 6.5 Timeline
#### Purpose
Guest に紐づく情報を **時間軸**で辿り、**その人との時間の積み重ね**を確認する。単なる操作ログではない。
#### Current Problem
「前回こう言っていた」「その時はこういう事情だった」が共有されず、**同じ質問を繰り返す**・**触れない方がよい話題に触れる**リスクがある。最新メモだけが正として古い文脈が消えると、誤解が生じる。
#### Current Problem（データの扱い）
- 現在は変わっている情報
- センシティブな情報
- 触れない方がよい情報
- 誤って上書きしてはいけない情報  
が存在しうる。**最新だけを正として古い情報を上書きする**設計は採用しない（`04_DOMAIN_MODEL.md` で具体化予定）。
#### Behavior Change

- 接客の前後に、スタッフが **過去の出来事を時系列で確認する**行動が生まれる。
- 気づきを **追記**する行動が生まれる（上書き文化にしない）。
- 次のシフトのスタッフが **同じ Timeline を読んで引き継ぐ**行動が生まれる。

#### User Flow

```
Guest Summary
  ↓
Timeline
  ↓
（閲覧）
  ↓
（必要時）新規エントリ追記
```

#### Information Displayed

MVP で実装する **イベント種別**（すべて必須ではない。構造を優先）：

| 種別 | MVP |
|------|-----|
| 過去の滞在（Stay） | 含める |
| スタッフの短いメモ（Memory の最小形） | 含める |
| 会話・申し送り | メモとして含める |
| 食事・好み・特記事項 | **既にあれば表示**（専用 UI は増やさない） |
| システムイベント（紐付け完了等） | **要検証** |

将来の種別は **将来検討**。MVP で全種別を実装しない。

#### Input

- **短いテキストメモの追記**（最小入力）
- なぜ入力するか：接客で得た気づきを **次のスタッフ・次の滞在**に残し、行動として「振り返る」ため（原則 12）
- 削除・編集ポリシー：**未決定**（センシティブ情報を踏まえ ADR 化）

#### AI Usage

- Timeline 本文の **要約入力**として Guest Summary の AI が利用（6.4）
- Timeline 上での自動生成エントリは MVP 必須ではない（**未決定**）

#### Acceptance Criteria

- Guest に紐づく滞在とメモが **時系列**で表示される。
- 新規メモを **追記**できる（上書き一本化ではない）。
- スタッフが「前回のことを確認してから接客した」と説明できる運用が可能。

#### Open Questions

- センシティブ情報のマスキング・権限（**未決定**）
- 訂正（誤記）の扱い：追記 vs 失効フラグ（**要検証**、`04_DOMAIN_MODEL` 連携）

### 6.6 Paper Output
#### Purpose
Today's Brief を **紙で出力**し、朝礼・申し送り・フロント周辺・厨房・バックヤードなど、**紙文化のある現場**でチームが同じ情報を共有する。
**MVP 機能として含める**（確定：本仕様タスク）。印刷レイアウトの詳細は **未決定**。
#### Current Problem
画面を見られる人と見られない人で情報が分かれ、**朝礼で口頭だけ**だと抜け・圧縮が起きる。フロント以外は「今日誰が来るか」の文脈を持てない。
#### Behavior Change
- 朝礼やシフト開始時に、**Today's Brief から紙を出して共有する**行動が生まれる。
- 紙を見たスタッフが **到着 Guest の名前と最小文脈**を意識して動く行動が生まれる。
- **全情報を紙に出さない**運用（安全）を前提に、必要な情報だけを選ぶ行動が生まれる（出力範囲は仕様で制限）。
#### User Flow

```
Today's Brief
  ↓
「印刷」操作
  ↓
プレビュー（範囲：未決定）
  ↓
印刷 / PDF 保存（方式：未決定）
```

#### Information Displayed（紙上）

**原則：必要な情報だけを安全に出力**

検討候補（**採用項目は未決定**）：

- 本日到着・出発の一覧（名前・日程の最小セット）
- Guest Resolution 未完了の注意
- **含めない方針**：Timeline 全文、センシティブメモの詳細、AI 要約の長文、不要な個人情報

#### Input

- 出力範囲の選択（当日全体 / 到着のみ等：**未決定**）
- 印刷実行

#### AI Usage

- MVP では **紙面生成に AI 必須としない**（レイアウトはテンプレート想定：**未決定**）

#### Acceptance Criteria

- Today's Brief の **当日情報**を、紙または PDF 相当で **共有可能**。
- 紙に **全 Guest 詳細・全 Timeline** が漏れない設計になっている（具体フィルタは未決定だが、受入時にチェック）。
- パイロット施設で **朝礼・申し送りで使う**試行ができる。

#### Open Questions

- A4 / 複数枚 / 厨房向け簡易版（**未決定**）
- PDF のみか物理印刷か（**未決定**）
- 02 上の「Paper 未定」は **フォーマット・運用詳細**を指す。機能としての Paper Output は本仕様で MVP に含める

## 7. AI Scope
### MVP で使う（確定方針）
| 用途 | 内容 |
|------|------|
| 要約 | Guest Summary における履歴・メモの圧縮 |
| 情報整理 | 長文の構造化表示の補助（**深度は未決定**） |
| フィルタリング | 当日確認に必要な注意の **見せ分け**（**要検証**） |
### 入力・出力の原則
- **入力**：Guest に紐づく Timeline / メモ / 滞在メタデータ（範囲 **未決定**）
- **処理**：要約・整理。Phase 2 の抽出は **将来検討**
- **出力**：スタッフが読むテキスト。人間が最終判断（原則 7）
### MVP で使わない（確定）
- 自動接客
- 自動判断（Guest 紐付けの自動完結）
- お客様へのサービス提案
- スタッフへの断定的な指示（「こう言え」等）
- お客様の評価・ランキング
### 未決定

- AI モデル、ホスティング、PII 処理、コスト上限

## 13. MVP Boundary

### この MVP で作るもの

1. **予約データが藍 ai に入る**仕組み（経路は未決定だが、状態は作る）  
2. **Guest Resolution**（人の確認付き紐付け）  
3. **Today's Brief**（ホーム）  
4. **Guest Summary**（体験 A）  
5. **Timeline**（時間の積層・追記）  
6. **Paper Output**（Brief からの安全な紙出力・レイアウト未決定）  
7. **AI による要約・整理**（Guest Summary 中心、過剰な自動化なし）

### この MVP で作らないもの

経営ダッシュボード、メール解析、自動接客、関係グラフ、清掃・教育・Community、高度 Memory、レビュー/LINE 連携、および §9 一覧のすべて。

**一行で**：*行動を変えるために、今日のお客様を理解し、予約を Guest につなぎ、時間の積層を辿れる最小の Hospitality OS。*

## 14. MVP 設計原則（仕様書への明記）

1. **機能ではなく行動を設計する**  
2. **情報量を増やすのではなく、理解を深める**  
3. **Guest を中心に情報をつなぐ**  
4. **現場の入力負担を増やさない**  
5. **AI は認知負荷を下げるために使う**  
6. **メニューは最小限にする**  
7. **人間が最終的な確認・判断を行う**  
8. **MVP では拡張性を設計するが、機能を先取りして実装しない**
