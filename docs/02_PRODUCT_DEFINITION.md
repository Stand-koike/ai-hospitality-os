# 02 — プロダクト定義（藍 ai）

**ステータス**：v0.1  
**前提**：本章の「確定」は、プロダクトオーナー提供ブリーフに明示された内容。それ以外は **仮説** または **未決定**。

---

## 1. プロダクトの目的

藍 ai が**最初に直接実現する**のは、「宿の価値向上」そのものではない。

**宿泊施設で働く人の行動を変えること**（確定）

### 因果連鎖（確定）

```
行動が変わる
  ↓
情報が残る
  ↓
情報が共有される
  ↓
お客様への理解が深まる
  ↓
接客が変わる
  ↓
再訪・関係性につながる
  ↓
結果として宿の価値が高まる
```

設計上の重要概念：**行動変容**

## 2. 基本原則（13 則）

| # | 原則 | 確度 |
|---|------|------|
| 1 | 予約は入口であり、人が中心。 | 確定 |
| 2 | お客様は単なる予約データではなく、一人の人として認識する。 | 確定 |
| 3 | 宿泊履歴は時間の積層として扱う。 | 確定 |
| 4 | Guest を中心にデータを紐付ける。 | 確定 |
| 5 | 思想として Relationship を重視する。 | 確定 |
| 6 | 効率化とおもてなしは相反しない。 | 確定 |
| 7 | 効率化は人の仕事を減らすためだけではなく、人が人らしく働く余白を作るために使う。 | 確定 |
| 8 | 必要な情報を、必要な部署・担当・タイミングに、必要な形で届ける。 | 確定 |
| 9 | 情報量を増やすのではなく、「その人を理解しやすくすること」を重視する。 | 確定 |
| 10 | AI は人の代替ではない。人の気づきを整理し、価値へ変換する補助者として使う。 | 確定 |
| 11 | 現場の負担を増やす機能は作らない。 | 確定 |
| 12 | 「入力させる」のではなく、日常の接客で生まれた気づきを自然に残せる設計にする。 | 確定 |
| 13 | 意識改革を直接行うのではない。行動が変わる仕組みを作り、その結果として意識や文化が変わることを目指す。 | 確定 |

## 3. ターゲット

### 初期ターゲット（確定）

本来価値を持っているが、**人手不足・情報共有不足・仕組み不足**などで価値を十分発揮できていない宿。

想定施設タイプ（確定）：

- 家族経営旅館、小規模旅館、地域密着型宿、小規模ホテル、民宿、高付加価値民泊、その他関係性を大切にする宿

### クラス感（確定＋未決定）

- 高級宿のみではない。**初期は主に B〜C クラス**（確定）
- A クラスにも将来的に価値提供（確定）
- **B〜C の価格帯・地域の定義：未決定**

### モデル施設（パイロット：確定 2026-09-18）

| 項目 | 内容 |
|------|------|
| 施設数 | 1 |
| 経営 | 個人経営 |
| 客室数 | 7 室 |

施設名・地域・利用 OTA：**未決定**（[decision-log/20260918-model-property-pilot.md](../decision-log/20260918-model-property-pilot.md)）

## 4. 解く課題と、あえて差別化しない領域

### テーブルステークス（重要だが差別化要素にしない：確定）

アレルギー、食事、部屋希望、支払情報など、一般的 PMS が扱う業務情報。  
藍 ai でも **当たり前にできること**として扱う（MVP での実装深度は [03_MVP_SPEC.md](03_MVP_SPEC.md) で定義）。

### 藍 ai が深掘りする情報（確定）

過去の会話、人柄、好み、家族構成、趣味、過去の出来事、記念日、前回の滞在、スタッフが感じたこと、宿との関係性 など **人に紐づく情報**。

**ただし**、最初から大量入力させない（確定）。

## 5. MVP で再現する体験

| ID | 体験 | 確度 |
|----|------|------|
| A | 今日来るお客様を短時間で理解できる | 確定 |
| C | 予約が入った瞬間、過去のお客様とのつながりが見える | 確定 |

### MVP 機能ブロック（確定：名称と存在）

| # | 機能 | 行動変容（設計問いへの回答） |
|---|------|------------------------------|
| 1 | 予約データの取り込み（OTA 等） | 予約情報を一箇所で追い、到着前の準備に使う |
| 2 | Guest Identity / Guest Resolution | 過去の関係性があるか確認し、Guest に紐付ける |
| 3 | Today's Brief（ホーム） | チェックイン前に今日のお客様を確認する |
| 4 | Guest Summary | 選択したお客様の文脈を一望する |
| 5 | Timeline | 時系列で過去を振り返り、配慮すべき情報も踏まえる |
| 6 | Paper Output | 朝礼・紙でチームに共有する（**フォーマット・要否の詳細：未決定**） |

### 予約データの取得（PO 決定 2026-09-18）

- **MVP に予約メール解析は含めない**（Make / Sheets / Calendar 等のメール解析パイプラインはスコープ外）
- 体験 C を満たすため、**別の取り込み経路**が必要：**未決定**（例：OTA API、CSV、手動 — いずれも仮説、採用は `03_MVP_SPEC` で決定）
- 詳細：[decision-log/20260918-no-reservation-email-parsing.md](../decision-log/20260918-no-reservation-email-parsing.md)

## 6. MVP で作らないもの（確定）

高度な Memory 管理、家族関係グラフ、高度な Relationship Graph、AI 接客提案/自動接客、レビュー分析、LINE 統合、清掃管理、スタッフ評価、教育、Community、高度な分析、経営ダッシュボード、他業界展開。

**原則**：拡張性は設計するが、MVP では実装しない。Guest ID 等の基礎は拡張可能に。

## 7. AI 利用方針

| Phase | 内容 | MVP |
|-------|------|-----|
| 1 | 要約 | **中心** |
| 2 | 情報抽出・フィルタリング | 将来 |

**未決定**：Phase 1 要約の入力ソース範囲、モデル選定、オンデバイス/クラウド、個人情報の扱い。

## 8. ホーム画面とナビゲーション（確定：思想）

- ホーム名称：**Today's Brief**
- 目的：今日のお客様を理解する（売上・KPI・グラフ中心にしない）
- 想定フロー：Today's Brief → 本日到着一覧 → Guest 選択 → Guest Summary →（必要なら）Timeline
- UI 原則：メニュー最小、ダッシュボード化しない、「何を見ればいいか分からない画面」を作らない
- 3 タップ以内は目安（現場の利用速度を最優先）

**未決定**：MVP のメニュー項目の最終本数（ブリーフ仮：今日・お客様・予約・Memory・設定 → MVP でさらに削減可）

## 9. データモデル（思想レベル）

主語は **Guest**。Relationship を重視。

```
Guest
 ├── Reservation   （一時的なイベント）
 ├── Stay
 ├── Memory        （時間の積層）
 ├── Relationship
 └── Briefing
```

詳細は `04_DOMAIN_MODEL.md` で MVP 最小エンティティに落とす。

1. 現場の行動が本当に変わるか

**未決定**：パイロット宿での観察方法、定量指標、再訪率の取り方（データ源）。

---

## 12. 開発ルール（ブリーフより）

1. 既存仕様を勝手に変更しない  
2. MVP に不要な機能を勝手に追加しない  
3. 実装前に仕様上の問題を指摘する  
4. 技術的に可能でもユーザー価値が弱ければ提案しない  
5. 「AI だから」だけで AI を使わない  
6. 現場の入力負担を増やさない  
7. 画面数を増やしすぎない  
8. 将来拡張可能なデータモデルを意識する  
9. Guest ID を長期的基盤として扱う  
10. 不明点は勝手に決めず、質問する
