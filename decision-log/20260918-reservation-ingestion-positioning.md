# 決定：予約取り込みのプロダクト位置づけ（PMS 共存・CSV / スプレッドシート）

- 日付：2026-09-18
- ステータス：承認（PO 指示）
- 関係者：プロダクトオーナー

## コンテキスト

Phase 1 着手前に、予約データの最小経路を整理する際、**別案件の Make / Google Sheets / Google Calendar 運用実績を藍 ai の前提に混在させない**よう明確化が必要になった。

営業・Product 化を見据え、宿泊施設側にはすでに **予約管理ソフト（PMS 等）** がある前提で、藍 ai はそれと **競合しない**。

## 決定

1. **藍 ai は PMS の代替ではない。** 予約の正本は各施設の予約管理ソフト（または個人経営における運用手段）に置き、藍 ai は **Guest-centered の理解・記録・共有**に集中する。
2. **Phase 1 の取り込み前提**（いずれも藍 ai 内の機能として設計する）：
   - **手動登録**（フォールバック・単発予約）
   - **CSV インポート**（各ホテル予約管理ソフトの **CSV 出力**を想定）
   - **スプレッドシート運用**（**個人経営**など PMS を使わない／併用しない施設向け）— **藍 ai 定義の CSV テンプレート**で取り込み（スプレッドシートは編集 UI、取り込み形式は CSV と同一経路）
3. **Make / Google Sheets / Google Calendar を連携前提・参照実装として扱わない。** 他案件の自動化基盤を藍 ai の仕様・営業ストーリーに含めない。
4. **OTA / PMS の API 直接連携**は、Phase 1 の最小経路の **前提にしない**（将来の正式 Integration 候補）。

## 理由

- プロダクト境界の明確化（Hospitality OS vs PMS）
- 営業時に「既存予約ソフトと併用」が説明できる
- 7 室個人経営パイロットと、将来の B〜C クラス施設の両方に、**実装コストの低い共通経路**（CSV）を置ける

## 行動変容への影響

- スタッフは **予約管理ソフト（またはスプレッドシート）で予約を管理した後**、藍 ai に **エクスポート／取込または手入力**で予約を載せ、Guest Resolution と Brief に進む。
- 藍 ai を「予約の唯一の入力画面」にしない設計も許容される（**二重入力を最小化**する UX・運用は Product 化で検証）。

## 代替案

- OTA API / PMS API の直接連携のみで Phase 1 を始める → **却下**（過剰実装・営業前提と不一致）
- 予約メール解析 → **MVP 外**（[20260918-no-reservation-email-parsing.md](./20260918-no-reservation-email-parsing.md)）
